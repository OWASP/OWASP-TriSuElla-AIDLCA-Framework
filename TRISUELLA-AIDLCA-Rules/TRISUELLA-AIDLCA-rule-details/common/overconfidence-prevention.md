# TRISU Overconfidence Prevention & Strategic Discovery

## Problem Statement

The **TRISU** framework must resist "Logic Overconfidence"—the tendency for AI agents to make assumptions about strategic intent without sufficient clarification. Assumptions violate the **TILLIT** (Trust) pillar and create functional drift that compromises the **SISU** (Resilience) of the final system.

---

## The "Zero-Assumption" Invariant

TRISU enforces a **Zero-Assumption** policy across all lifecycle stages. If an instruction or context is not 100% deterministic, the agent MUST trigger a **DUGNAD** (Collaboration) checkpoint.

### 🔴 Red Flags of Overconfidence:
- Progressing through a phase with zero Stewardship Questions on a complex project.
- Accepting vague user intent (e.g., "Standard security", "Normal performance") without defining the specific TRISU rules applied.
- Skipping entire configuration categories (e.g., NFRs) without a documented strategic exclusion.
- Inferring architectural boundaries without explicit steward confirmation.

---

## The TRISU Discovery Protocol

### 1. Default to Questioning
**Mantra**: When in doubt, ask the question. Over-clarification is a feature of high-integrity governance; under-clarification is a failure of trust.

### 2. Comprehensive Category Evaluation
Agents MUST evaluate ALL relevant TRISU categories in every stage. Exclusion of a category (e.g., skipping 'Cloud Security' in an on-premise project) must be an active, justified decision, not a passive omission.

### 3. Semantic Ambiguity Detection
Agents MUST proactively detect and resolve non-deterministic language in steward responses:
- **Vague Quantifiers**: "mostly", "partially", "some".
- **External References**: "like our other project", "standard industry practice".
- **Hedged Intent**: "maybe", "probably", "we think".

### 4. Mandatory Flux Resolution
If a steward's response creates a logical conflict (e.g., "High Availability" but "Minimal Infrastructure"), the system MUST halt and force a resolution via a **Clarification File** before any construction begins.

---

## Success Criteria for Discoverability

- **High-Entropy Questions**: Every Stewardship Question must offer distinct, meaningful strategic paths.
- **Traceable Intent**: Every requirement in the final system can be traced back to an explicit steward decision.
- **Structural Integrity**: The final build aligns 100% with the **TRISU-TEST** invariants defined during discovery.

---

## Maintenance & Evolution

This guide MUST be referenced when:
- Adding new jurisdictional extensions (e.g., **TRISU-ISO-IND**).
- Updating existing stage logic to handle more complex multi-agent orchestrations.
- Reviewing system performance for "Assumption Drift."

> **Core TRISU Invariant**: The cost of a question is minimal; the cost of an incorrect assumption is systemic failure.
